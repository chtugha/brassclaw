# Recipe-owned source compiler

The installer retains exact component drafts, then qualifies the packaged
source-only workflow through its closed `system_seed` owner. It currently produces
quarantined base-prompt and Prefix-Maker packages. The qualified program is private:
it returns a durable receipt and is not advertised as an ordinary chat Recipe.
Generate jobs, accepted model designs, target tokenization, activation and cache
warming remain separate work; qualification alone does not enable their WebUI actions.

`brassclaw_skills::prefix_compiler_components` supplies reusable PythonCode for
whole-source segmentation, compilation stages and receipt formatting. It reuses
`prefix_reference_components` for rendering, `utf8_digest_components` for one JSON
Tool usage, and `prefix_generation_components` for immutable retention. The
source compilation Recipe orders those components; Rust performs hashing,
storage, transport, integrity and kernel checks.

## Input and provenance

The `brassclaw-prefix-source-snapshot/1` input contains `profile`, `release`,
`header`, `evidence_view`, complete `sources` and three original `procedures`.
Each source declares its canonical relative path, kind, disposition, reason and
complete UTF-8 text. The seven component/architecture guides are mandatory;
Prefix-Maker additionally requires its dedicated reference. Component-library
coverage is not implied by including those guides.

The owner must build that snapshot from its retained source/design/code selection.
Caller-supplied procedure text does not prove which compiler ran. Keep the complete
retained graph and original procedures with the task; do not look up latest during
execution. The compiler preserves originals by content hash, full evidence cards,
source inventory, rendering/range data, procedure files and immutable manifest.
Literal v1 and exact-unit-deduplicated v2 are supported; neither silently summarizes
or clips originals.

## Execution

1. Validate the canonical positive decimal profile revision.
2. Prepare complete sources and the first ordered hash batch in PythonCode.
3. Hash through `digest_utf8_texts`, then prepare references in PythonCode.
4. Hash evidence identities, then render in PythonCode.
5. Hash all artifacts, then prepare the generation identity in PythonCode.
6. Hash the identity, then finalize the package in PythonCode.
7. Retain once through the existing immutable-generation usage.
8. Format the actual quarantined retention result as the internal task receipt.

Every hash and retention dispatch has its own ToolSkill/executable pair. Pure
stages have no artificial Tool binding. Runtime values remain typed data; the
compiler does not execute source references or turn them into Python programs.
Loading the library performs no usage. Hashes use exact UTF-8 bytes without
Unicode or newline normalization. One hash batch permits at most 8192 strings;
exceeding that technical bound fails the build. A qualified batching workflow is
required before claiming larger complete-library coverage; removing sources to
fit the bound is not supported.

The final string is `prefix-generation:<profile>:<retained package SHA-256>`.
It is neither approval nor proof of task completion. The admission owner must
verify the actual correlated immutable row, dispatch/effect records, cancellation
and settlement before reporting completion. A lost result never authorizes replay
of Retain or of the whole Recipe. Source-only manifests remain unmeasured,
activation-ineligible and cache-unverified.

## Archive references and input evidence

New output inventories use `brassclaw-prefix-generation-sources/1`. Their
`artifact` fields resolve directly to the retained `raw/<SHA-256>` originals.
`input_artifact` points to `source_snapshot.json` for the Monty stages or
`input_sources.json` for the offline compiler. The former preserves the exact
canonical task snapshot; the latter preserves the exact original input manifest,
including its original formatting and input-package object names. Profile design
metadata is retained for literal v1 builds too.

Historical `brassclaw-prefix-source-package/1` output inventories remain readable;
their `artifact` fields belong to the input package namespace. Resolve their
archived originals by the established raw-by-hash layout rather than interpreting
those old fields as generation file paths. Immutable historical artifacts are not
rewritten. The importer checks new archive/input relationships, citation identities,
full ranges and counts independently of the generic package hashes. None of these
integrity checks qualify knowledge or execution.

## Internal Recipe completion

Compiler work produces a durable receipt instead of a chat reply. The task owner
selects one exact inspected program and typed input snapshot. The global Python
root reads that selection and runs its prepared Recipe flow; the Rust adapter
executes only the requested step. An internal task cannot resolve chat intents,
select an additional named Recipe, publish a reply or invoke unrelated root ports.
Its receipt must be checked against actual native answers and durable generation
bytes before completion is accepted. A nonempty string alone is insufficient.

The development observer uses that same Python flow in a bounded contained
worker and closes its private claim after shutdown/reaping. It retains observations
without granting bootstrap approval or exposing a production worker service.
Negative checks distinguish an intended contained Python rejection from transport,
resource or process failure. Native invocation records must cover the whole run,
match the selected Recipe/binding and observed argument/answer fingerprints, and
retain their actual attempt counts. Production Generate admission still depends
on closed installation qualification and durable job integration.


## Closed installation qualification

`bootstrap_compiler_approval` verifies the exact packaged dependency graph, actual
native implementations, captured Monty worker and inspection/validation sources.
It reuses the existing canonical Retain approval. Its Q1 intent commits before
behavioral effects. Eight fixed cases run through the global Python Recipe flow;
the owner rereads their admitted selections, invocation arguments/answers/attempts,
independent UTF-8 digests, complete originals, literal/deduplicated views and
immutable receipts before committing behavior and hash-usage approval together.

Completed proof reuse performs no new dispatch. An incomplete intent requires
reconciliation and cannot replay the cases. Operator Tool blocks remain effective.
Synthetic fixture artifacts carry a qualification namespace to avoid upgrade
collisions with earlier profile revisions. That namespace affects validation
metadata; it is not a production prefix design setting. CRLF YAML and embedded
model control tokens remain exact in archived originals and safely literal in the
rendered view. Model/cache quality stays unqualified.

Native acceptance is recorded in
`target/validation/prefix-registry-artifacts-p6m1aifn/accepted.json`. It includes
private association pinning and public-route denial, immutable-record-safe intent
rejection, repeated coherent proof readback, source/archive checks, large-value
storage and all four domain compiler regressions. It applies to that frozen source.

## Durable snapshot jobs

`RebornRuntime::submit_prefix_generation_snapshot` is a low-level source-only
submission boundary. Its actual runtime/PG integration passes in
`target/validation/prefix-registry-artifacts-c5z_1d40/accepted.json`, together with
strict linting, result contracts and standalone consumer regressions. It retains the first canonical
snapshot, profile revision, compiler selection and data scopes under the existing
run UUID, then submits through ordinary durable turn admission. A reconnect reads
that definition; it does not replace sources or start another task executor.
The host resolves only an exact qualified compiler selection. Python owns the
Recipe stages; current kernel policy and native effect journaling still apply.
The final internal receipt must match actual immutable output and original inputs
before ResultOnly settlement. No assistant reply is fabricated.

This boundary is not the WebUI Generate action, an authoritative source collector,
a complete-library coverage claim, an accepted model design or activation. The
remaining profiles and normal Generate UI stay gated until their complete source,
target and approval paths pass. Unknown or incompatible retained compiler revisions
fail closed pending recovery; they never silently use the newest revision.

## Contained offline model encoding

The fixed `brassclaw_model_encoding` engine is available through the retained
Monty utility worker's `EncodeModel` operation (utility protocol 4). It renders
ordered chat contexts and measures complete unpadded/untruncated token IDs,
returning hashes/counts and common-prefix hashes rather than large token arrays.
JSON uses Python-compatible ordering, spacing, escaping and float round trips.
No template filesystem loader, remote tokenizer code or provider is involved.

Frozen receipt
`target/validation/prefix-registry-artifacts-dvpfuk_0/accepted.json`
covers focused engine tests, the independent offline Hugging Face AutoTokenizer
oracle over retained Ornith originals, and real contained-worker measurement,
invalid-input rejection and deadline handling. The fixture explicitly supplies
1 GiB preparation memory and a 120-second deadline; it does not alter production
defaults. This proves the tested offline encoding path, not universal model
compatibility, server identity, attention/recurrent cache reuse or answer quality.

The native model-artifact adapter and canonical encoding-usage drafts still need
production-native/association acceptance before generation Recipes can select
and use them as an approved dependency. Generation/design acceptance, complete
source capture, model context headroom, cache qualification and activation remain
separate workflow steps.

The effective-template adapter additionally keeps original model-template identity
separate from a supplied template. Candidate templates are bounded rendering data;
measuring them grants no design acceptance. MiniJinja compatibility is explicit:
`vendor/minijinja-compat` supplies eager sequence concatenation, and the environment
makes `None is iterable` false. The source template remains byte-identical. The
four-test/contained-worker receipt is
`target/validation/prefix-registry-artifacts-33w6ysc2/accepted.json`; the independent
12-context full injected-template equality receipt is
`target/validation/prefix-encoding-reproduction-xk42v_67/accepted.json`.
Native DB/Recipe bootstrap and serving/cache acceptance remain separate.

Retained-run prefix lookup now returns a typed error for a missing/expired capture
or scope mismatch. It never substitutes the newest catalogue. The ordinary global
matched/No-Match regression passed in
`target/validation/prefix-registry-artifacts-tvsgm75_/retained-prefix-accepted.json`.
This does not yet implement full model/design/generation restoration after restart.

Observed core capacity is still too large for the historical 131,072-token target:
the real source-only v2 native measurement contained 141,820 framed tokens. The
originals and failed generation remain retained. A successful offline measurement
does not make that artifact eligible for activation or justify clipping mandatory
content or silently changing server settings.
