# monty.composition

## 1. Legacy components containing Python code to update and convert

This list contains class-22 PythonCode components and their identified legacy Skill usage companions: **101 conversion candidates** after reviewing **134 distinct seeded PythonCode names**. **92 Skill companions** are grouped with their code so that a usage is converted once. Recipes, Actions, Tools, ToolSkills, prose-only overviews, catalogues and class-10 roots are excluded from the list. Each link identifies the seeder call or generated definition that installs that name; UUIDs are instance-assigned and must be resolved during implementation.

Under [skills.md §§1, 3 and 7](../../skills.md), a Skill comprises prose plus explicitly associated PythonCode; the stored prose is never executed. The 169 legacy Skill seed calls were inspected, including constant and inline bodies. They contain usage prose, signatures, data examples and code references, not separate executable entry points. The companions below are historical usage/reference mappings inferred from the seed bodies and surrounding workflows, **not verified persisted v3 associations**. Explicit pc references and matching one-Tool usage descriptions qualify; merely mentioning Python syntax or several Tools in an overview does not. The range Skill is covered by the foreseen interval usage; the separate parse Skill is covered by the typed JSON example, as recorded in section 3.

The follow-up [component-by-component coverage audit](monty.composition.coverage.md) checks every original entry and companion against later seeds and concrete plans. It moved nine validator-owned tasks and eight redundant dispatch bodies out of this list, retaining relevant Skill usage companions with canonical executors. Partial overlap leaves distinct contract work here; an existing Tool or a plan describing the same old component is not a replacement.

The short changes below supplement the common v3/Monty acceptance requirements in section 5. A fixed body with no placeholders may still need a new revision, usage association and result contracts. Section 3 records the 33 excluded PythonCode names and applicable Skill dispositions and their reuse destinations; “foreseen” means design/planned work, not an activated component.

## 5. Conversion criteria

### V3 usage and assembly contract

The binding authorities are [recipe.md](../../recipe.md), [skills.md](../../skills.md), [tools.md](../../tools.md) and [toolskills.md](../../toolskills.md), with the installation-seed exception and current lifecycle status in [AGENTS.md](../../AGENTS.md). Apply their complete contracts, including these requirements:

- A Skill describes one Tool usage and explicitly associates its executable code. Reuse compatible code across several usages with separate reviewed argument/result contracts. Move broad overviews to Extension documentation and workflow sequencing to Recipes. Pure helpers remain PythonCode without an artificial ToolSkill or Skill wrapper.
- Each persisted component step contains one stable UUID, using the actual `knowledge`/`stepnumber` schema and exact input-reference grammar. A normal Tool usage has a Rust ToolSkill binding step immediately followed by its associated Orchestrator PythonCode. Independent calls need independent execution steps. Internal pure-code dependencies need explicit pinned compilation support.
- Bind step-local values through `inputs["local_name"]`. Remove source placeholders, quoted JSON slots and access to ambient `state`/previous-result variables. Declare recursive list/object contracts, extra-field rules, nullability, bounds and defaults. Missing and null differ; defaults apply only to missing consumer inputs. Typed producer results feed later consumers without stringification or source reconstruction.
- Keep stable component identities and create immutable successor revisions. A task-start catalogue snapshot pins the Recipe revision, variant, exact step link/input layout, complete code graph, associations, approvals and actual retained Tool implementations. Child execution, retries and resumes retain this selection.
- Association approval is separate from task selection and individual component validation. Record exact reviewed revisions/checksums and dependency combinations. Installed edits need authored Q1, behavior evidence and human Q2. Reviewed shipped successors use the controlled noncircular `system_seed` integrity/Q1/behavior path without extra installed-instance human Q2. A source/status label is insufficient.
- ToolSkill metadata neither executes nor grants access. Resolve actual Tool UUID, callable, capability and retained adapter; verify parameters/results before effects. Check live global Tool policy and technical constraints at every dispatch and retry, independently of fixed component versions.
- Errors, cancellation and unknown effects remain classified failures. Persist positive attempt counts and dispatch/effect state. Retry only eligible outcomes with verified read-only or durable deduplication evidence. A timeout is not evidence that no effect occurred; completed effects never replay because later validation or posting failed. Only actual No-Match enters Tier 2. All shell and spawn-subagent Recipes are Tier 1.

### Monty parsing and semantics

Use the **actual BrassClaw-pinned Monty build** and retained adapter as the acceptance target. The vendored [Monty control crate](../../vendor/monty-control/crates/monty/Cargo.toml) and [upgrade evidence](../../tests/monty_v1_upgrade/README.md) identify the local integration; record its exact upstream revision, local patch/artifact checksum and effective settings in conversion evidence. Rolling upstream documentation may describe behavior beyond that artifact. A CPython syntax check alone is insufficient.

Monty parses/compiles source at construction and host calls suspend for host completion. Validate each exact retained body before effects and exercise the actual suspension/resumption path. Monty's last expression supplies its output; BrassClaw also requires assigned `result`. Verify the adapter's wrapper/result extraction rather than appending arbitrary source or assuming an assignment alone is a returned value. Keep immutable source and typed arguments separate. See the [Rust quickstart](https://pydantic.dev/docs/monty/quickstart/rust/) and [host function contract](https://pydantic.dev/docs/monty/concepts/host-functions/).

Check imports, builtins, keyword arguments, exception handling and comprehension behavior against supported Monty semantics. Generator expressions currently materialize lists; do not infer lazy streaming. Unsupported constructs such as `yield` generators, structural matching and asynchronous iteration/context managers need different implementations. Upstream `eval`/`exec` support is **not** permission to use them: BrassClaw's retained inspector rejects executable intrinsics and forbidden ambient access such as `os`, `subprocess` and `open`. See [language limitations](https://pydantic.dev/docs/monty/limitations/language/) and [eval/exec semantics](https://pydantic.dev/docs/monty/limitations/eval_exec/).

Monty's `re` implementation differs from CPython. Test UUID/name validation with full-string matching, including trailing newlines; test supported APIs instead of assuming `re` compatibility. Tool-side grep uses its own engine and needs separate evidence. Encode URLs from UTF-8 bytes, not Unicode code-point numbers. See [regular expressions](https://pydantic.dev/docs/monty/limitations/re/) and [encoding support](https://pydantic.dev/docs/monty/limitations/encoding/).

Monty `json` supports a limited parsing/serialization surface. Do not assume file-based load/dump, encoder/decoder classes or unsupported hooks. Parsing is not recursive schema approval; nonfinite numbers require rejection under the chosen usage contract. When duplicate-key rejection or other unsupported parsing semantics are required, use a verified strict host parser rather than inventing a Python API. See [JSON limitations](https://pydantic.dev/docs/monty/limitations/json/).

The host boundary must carry only the declared typed value shapes. Reject booleans where integer counts are required, out-of-profile numbers, cycles, opaque objects and unsupported/lossy conversions. Do not accept repr strings or depth-limit placeholders as ordinary valid application data. Preserve isolation across tasks/attempts and intermediate results across supported waits. See [host values](https://pydantic.dev/docs/monty/limitations/host-values/).

Enforce compute time, memory and structural limits through the shared service's supported accounts; awaiting a Tool is not executing VM time. Do not add artificial token caps when token budgets are disabled. Monty snapshots require compatible trusted integrity-checked data and do not establish durable effect reconciliation. Task failure must not trigger whole-Recipe replay or a replacement per-chat VM. See [resource limits](https://pydantic.dev/docs/monty/concepts/resource-limits/), [snapshots](https://pydantic.dev/docs/monty/concepts/snapshots/) and BrassClaw's stricter supervisor/recovery rules in [tools.md](../../tools.md).

## 10. Goal: reusable PythonCode assembled by Recipes

Build a large library of **Recipes composed from small reusable PythonCode units**, rather than a large library of complex task-specific Python programs. A PythonCode unit performs one coherent transformation or one declared Tool usage. A Recipe supplies the task workflow: input capture, preparation, Tool binding/calls, data handoff, branching where supported, completion and failure handling. Small does not mean one line: keep validation and an operation's necessary local processing together when splitting would produce fragments with no independent reuse.

A split is justified only when a resulting part has another named consumer here or a credible concrete future usage, with a stable useful input/result contract. Do not create a component for every comparison, concatenation or private function. Reuse the same immutable code across compatible Skills/Recipes, and keep different usage contracts explicit. Fixed command/pattern/endpoint values usually become reviewed Recipe data, not a separate executable. Pure logic is PythonCode, not a zero-Tool Skill. A Skill remains one Tool usage with prose and associated executable code; a Recipe coordinates multiple usages. The protected global root remains a lifecycle component.

The component-by-component assessment is in section 11. [Concrete implementation sections](monty.composition.implementation.md) cover every retained legacy entry, every newer entry, their Skill companions and every proposed reusable extraction. Proposed helper labels are design handles, not allocated names or UUIDs. Resolve an existing compatible component first; allocate a new stable UUID only if none exists. A replacement workflow retires the monolith from new admission after acceptance, while keeping old task-selected artifacts.

### 10.1. Design the Recipe so IBS can assemble the right program

1. State the goal and observable completion. Classify effects and Tier: deterministic eligible workflows can be Tier 0; shell/spawn-subagent and explicit creative model work are Tier 1. Define captured inputs and recursive result schemas before arranging steps.
2. Resolve canonical components. Each persisted component step has exactly one stable UUID in `include`. Tool use normally has a `knowledge: "rust"` ToolSkill step immediately followed by the matching `knowledge: "orchestrator"` PythonCode step. Pure logic has only the executable step. Independent Tool calls are separate pairs; internal pure composition is allowed only with pinned dependencies and supported assembly.
3. Bind typed inputs separately from source. Use whole metadata references such as `{{vars.path}}`; each code unit accesses a local `inputs["path"]`. A preceding result/field supplies the next local input through the typed layout. Never paste a value, JSON string, arithmetic expression or prior result into Python source. Consumer defaults apply only to missing inputs.
4. Use the actual `step_descriptions` / `stepnumber` / `knowledge` / `type: "component"` schema and a selected variant's exact `step_link`. `channel`, `step_id` and ad hoc flow fields are not insert fields. `type: "text"` annotates; it does not execute. The typed layout below is a distinct versioned layout document, not an invented field added to a legacy step.
5. IBS and composition select one approved catalogue generation, retain the Recipe/variant/layout and all exact revisions/checksums, associations, dependencies and actual Tool artifacts, then create the ephemeral BuildInstruction and prepared program references. Recipes hold stable UUIDs; selection supplies exact versions. Matching, assembly, child execution and continuation retain the same selection.
6. Keep intermediate results owned by the task in Monty. Validate each producer before a consumer reads it, preserve missing versus null, and propagate failures. Bindings grant no permission; the kernel checks live global Tool policy before dispatch. Missing support or an incompatible approved combination is an assembly error, never a No-Match or permission to downgrade.
7. Qualify the complete Recipe combination and production path. Planned layouts, associations, adapters and flow support must exist before activation. Example Python parsing does not establish Monty, behavior or bootstrap acceptance. Installation seeds use reviewed noncircular system_seed qualification; installed edits use authored Q1/behavior/human-Q2.
