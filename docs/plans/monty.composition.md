# monty.composition

## 1. Legacy components containing Python code to update and convert

This list contains class-22 PythonCode components and their identified legacy Skill usage companions: **101 conversion candidates** after reviewing **134 distinct seeded PythonCode names**. **92 Skill companions** are grouped with their code so that a usage is converted once. Recipes, Actions, Tools, ToolSkills, prose-only overviews, catalogues and class-10 roots are excluded from the list. Each link identifies the seeder call or generated definition that installs that name; UUIDs are instance-assigned and must be resolved during implementation.

Under [skills.md §§1, 3 and 7](../../skills.md), a Skill comprises prose plus explicitly associated PythonCode; the stored prose is never executed. The 169 legacy Skill seed calls were inspected, including constant and inline bodies. They contain usage prose, signatures, data examples and code references, not separate executable entry points. The companions below are historical usage/reference mappings inferred from the seed bodies and surrounding workflows, **not verified persisted v3 associations**. Explicit pc references and matching one-Tool usage descriptions qualify; merely mentioning Python syntax or several Tools in an overview does not. The range Skill is covered by the foreseen interval usage; the separate parse Skill is covered by the typed JSON example, as recorded in section 3.

The follow-up [component-by-component coverage audit](monty.composition.coverage.md) checks every original entry and companion against later seeds and concrete plans. It moved nine validator-owned tasks and eight redundant dispatch bodies out of this list, retaining relevant Skill usage companions with canonical executors. Partial overlap leaves distinct contract work here; an existing Tool or a plan describing the same old component is not a replacement.

The short changes below supplement the common v3/Monty acceptance requirements in section 5. A fixed body with no placeholders may still need a new revision, usage association and result contracts. Section 3 records the 33 excluded PythonCode names and applicable Skill dispositions and their reuse destinations; “foreseen” means design/planned work, not an activated component.

## 5. Conversion criteria

### V3 usage and assembly contract

The binding authorities are [recipe.md](../../recipe.md), [skills.md](../../skills.md), [tools.md](../../tools.md) and [toolskills.md](../../toolskills.md), with the installation-seed exception and current lifecycle status in [AGENTS.md](../../AGENTS.md). Apply their complete contracts, including these requirements:

- A Skill describes one Tool usage and explicitly associates its executable code. Reuse compatible code across several usages with separate reviewed argument/result contracts. Move broad overviews to Extension documentation and workflow sequencing to Recipes. Pure helpers remain PythonCode without an artificial ToolSkill or Skill wrapper.
- Each persisted component step contains one stable UUID, using the actual `knowledge`/`stepnumber` schema and exact input-reference grammar. A normal Tool usage has a Rust ToolSkill binding step immediately followed by its associated Orchestrator PythonCode. Independent calls need independent execution steps. Internal pure-code dependencies need explicit pinned compilation support.
- Bind step-local values through `inputs["local_name"]`. Remove source placeholders, quoted JSON slots and access to ambient `state`/previous-result variables. Declare recursive list/object contracts, extra-field rules, nullability, bounds and defaults. Missing and null differ; defaults apply only to missing consumer inputs. Typed producer results feed later consumers without stringification or source reconstruction.
- Keep stable component identities and create immutable successor revisions. A task-start catalogue snapshot pins the Recipe revision, variant, exact step link/input layout, complete code graph, associations, approvals and actual retained Tool implementations. Child execution, retries and resumes retain this selection.
- Association approval is separate from task selection and individual component validation. Record exact reviewed revisions/checksums and dependency combinations. Installed edits need authored Q1, behavior evidence and human Q2. Reviewed shipped successors use the controlled noncircular `system_seed` integrity/Q1/behavior path without extra installed-instance human Q2. A source/status label is insufficient.
- ToolSkill metadata neither executes nor grants access. Resolve actual Tool UUID, callable, capability and retained adapter; verify parameters/results before effects. Check live global Tool policy and technical constraints at every dispatch and retry, independently of fixed component versions.
- Preserve classified errors, cancellation, unresolved effects and supported explicit waits/handles; unknown completion is not confirmed failure or success. Persist positive attempt counts and dispatch/effect state. Retry only eligible outcomes with verified read-only or durable deduplication evidence. A timeout is not evidence that no effect occurred; completed effects never replay because later validation or posting failed. Only actual No-Match enters Tier 2. All shell and spawn-subagent Recipes are Tier 1.

### Monty parsing and semantics

Use the **actual BrassClaw-pinned Monty build** and retained adapter as the acceptance target. The vendored [Monty control crate](../../vendor/monty-control/crates/monty/Cargo.toml) and [upgrade evidence](../../tests/monty_v1_upgrade/README.md) identify the local integration; record its exact upstream revision, local patch/artifact checksum and effective settings in conversion evidence. Rolling upstream documentation may describe behavior beyond that artifact. A CPython syntax check alone is insufficient.

Monty parses/compiles source at construction and host calls suspend for host completion. Validate each exact retained body before effects and exercise the actual suspension/resumption path. Monty's last expression supplies its output; BrassClaw also requires assigned `result`. Verify the adapter's wrapper/result extraction rather than appending arbitrary source or assuming an assignment alone is a returned value. Keep immutable source and typed arguments separate. See the [Rust quickstart](https://pydantic.dev/docs/monty/quickstart/rust/) and [host function contract](https://pydantic.dev/docs/monty/concepts/host-functions/).

Check imports, builtins, keyword arguments, exception handling and comprehension behavior against supported Monty semantics. Generator expressions currently materialize lists; do not infer lazy streaming. Unsupported constructs such as `yield` generators, structural matching and asynchronous iteration/context managers need different implementations. Upstream `eval`/`exec` support is **not** permission to use them: BrassClaw's retained inspector rejects executable intrinsics and forbidden ambient access such as `os`, `subprocess` and `open`. See [language limitations](https://pydantic.dev/docs/monty/limitations/language/) and [eval/exec semantics](https://pydantic.dev/docs/monty/limitations/eval_exec/).

Monty's `re` implementation differs from CPython. Test UUID/name validation with full-string matching, including trailing newlines; test supported APIs instead of assuming `re` compatibility. Tool-side grep uses its own engine and needs separate evidence. Encode URLs from UTF-8 bytes, not Unicode code-point numbers. See [regular expressions](https://pydantic.dev/docs/monty/limitations/re/) and [encoding support](https://pydantic.dev/docs/monty/limitations/encoding/).

Monty `json` supports a limited parsing/serialization surface. Do not assume file-based load/dump, encoder/decoder classes or unsupported hooks. Parsing is not recursive schema approval; nonfinite numbers require rejection under the chosen usage contract. When duplicate-key rejection or other unsupported parsing semantics are required, use a verified strict host parser rather than inventing a Python API. See [JSON limitations](https://pydantic.dev/docs/monty/limitations/json/).

The host boundary must carry only the declared typed value shapes. Reject booleans where integer counts are required, out-of-profile numbers, cycles, opaque objects and unsupported/lossy conversions. Do not accept repr strings or depth-limit placeholders as ordinary valid application data. Preserve isolation across tasks/attempts and intermediate results across supported waits. See [host values](https://pydantic.dev/docs/monty/limitations/host-values/).

Enforce compute time, memory and structural limits through the shared service's supported accounts; awaiting a Tool is not executing VM time. Do not add artificial token caps when token budgets are disabled. Monty snapshots require compatible trusted integrity-checked data and do not establish durable effect reconciliation. Task failure must not trigger whole-Recipe replay or a replacement per-chat VM. See [resource limits](https://pydantic.dev/docs/monty/concepts/resource-limits/), [snapshots](https://pydantic.dev/docs/monty/concepts/snapshots/) and BrassClaw's stricter supervisor/recovery rules in [tools.md](../../tools.md).

1. **Resolve identities and reuse destinations.** Produce a machine-readable ledger from the source inventory and installed catalogue: old name/UUID/revision/checksum, historical Skill companion, actual association status, canonical destination, dependencies and disposition. Resolve the illustrative interval usage and current reply/history packages before redirecting callers. Inspect overrides and retained tasks. Do not interpret a matching name, class or validated flag as an approved association.
2. **Define usage contracts before rewriting bodies.** For each listed entry, reconcile prose, actual primitive parameters, fixed arguments and recursive input/result/failure contracts. Establish one-Tool usage boundaries and pure helpers. Split multi-call read/tail/filter, trigger removal and memory append only as needed by their actual semantics. Reuse one compatible dispatcher with multiple reviewed usage associations; do not create a duplicate executor for each fixed selector. Specify new host support only when an existing primitive/adapter truly cannot implement the operation.
3. **Complete required retained assembly support.** Verify catalogue selection, typed IBS bindings, exact associations, internal dependencies and loaded aliases in the real startup/worker path. Implement missing store/runner support before activating code that depends on it. Never bypass it by executing Skill prose, metadata or an arbitrary returned source string. Keep the current compiler's restrictions until explicit supported changes and acceptance justify expansion.
4. **Convert and qualify in manageable families.** Start with zero-host lexical/encoding/formatting helpers and the canonical interval usage. Then convert read-only filesystem/time/JSON/HTTP retrieval and domain shaping. Follow with effectful memory/file/trigger/API writes, shell usages and authoring validators. Each family includes its Skill prose corrections and exact combination evidence; a parse-only batch is not complete. Prefix/bootstrap lifecycle wrappers excluded in section 3 remain with their existing owners.
5. **Validate through real Monty and host bindings.** Compile exact successor bytes, execute representative valid/invalid inputs in the pinned interpreter, and then exercise retained assembly and actual registered adapters in a controlled environment. Verify input isolation, outputs, policy, effects, cancellation, waits and retained selection, including failures before dispatch. Reuse unchanged evidence only under the development policy's identity conditions.
6. **Ship immutable packaged successors and coherent catalogue generations.** Qualify installation-owned seeds with package/artifact integrity, structural/Q1 and behavioral evidence, using noncircular bootstrap ownership. Preserve operator overrides and old selections. Installed authoring uses its separate human-Q2 path. Catalogue activation occurs only after the full selected dependency/association combination and production runner support pass their gates; do not activate incompatible rows and silently omit them during matching.
7. **Retire legacy execution admission after acceptance.** Redirect relevant Recipe callers to canonical UUIDs using the actual persisted schema. Prevent placeholder-composed or prose-derived programs from entering execution, including older composer/MCP surfaces. Remove old defaults only after selection and resume tests show that new tasks use approved successors while old tasks retain their artifacts. Retiring new admission is distinct from deleting historical rows or implementations.

## 10. Goal: reusable PythonCode assembled by Recipes

Build a large library of **Recipes composed from small reusable PythonCode units**, rather than a large library of complex task-specific Python programs. A PythonCode unit performs one coherent transformation or one declared Tool usage. A Recipe supplies the task workflow: input capture, preparation, Tool binding/calls, data handoff, branching where supported, completion and failure handling. Small does not mean one line: keep validation and an operation's necessary local processing together when splitting would produce fragments with no independent reuse.

A split is justified only when a resulting part has another named consumer here or a credible concrete future usage, with a stable useful input/result contract. Do not create a component for every comparison, concatenation or private function. Reuse the same immutable code across compatible Skills/Recipes, and keep different usage contracts explicit. Fixed command/pattern/endpoint values usually become reviewed Recipe data, not a separate executable. Pure logic is PythonCode, not a zero-Tool Skill. A Skill remains one Tool usage with prose and associated executable code; a Recipe coordinates multiple usages. The protected global root remains a lifecycle component.

The component-by-component assessment is in section 11. [Concrete implementation sections](monty.composition.implementation.md) cover every retained legacy entry, every newer entry, their Skill companions and every proposed reusable extraction. Proposed helper labels are design handles, not allocated names or UUIDs. Resolve an existing compatible component first; allocate a new stable UUID only if none exists. A replacement workflow retires the monolith from new admission after acceptance, while keeping old task-selected artifacts.

### 10.1. Design the Recipe so IBS can assemble the right program

1. State the goal and observable completion. Classify effects and Tier: deterministic eligible workflows can be Tier 0; shell/spawn-subagent and explicit creative model work are Tier 1. Define captured inputs and recursive result schemas before arranging steps.
2. Resolve canonical components. Each persisted component step has exactly one stable UUID in `include`. Tool use normally has a `knowledge: "rust"` ToolSkill step immediately followed by the matching `knowledge: "orchestrator"` PythonCode step. Pure logic has only the executable step. Independent Tool calls are separate pairs; internal pure composition is allowed only with pinned dependencies and supported assembly.
3. Bind typed inputs separately from source. Use whole metadata references such as `{{vars.path}}`; each code unit accesses a local `inputs["path"]`. A preceding result/field supplies the next local input through the typed layout. Never paste a value, JSON string, arithmetic expression or prior result into Python source. Consumer defaults apply only to missing inputs.
4. Use the actual `step_descriptions` / `stepnumber` / `knowledge` / `type: "component"` schema and a selected variant's exact `step_link`. `channel`, `step_id` and ad hoc flow fields are not insert fields. `type: "text"` annotates; it does not execute. The typed layout below is a distinct versioned layout document, not an invented field added to a legacy step.
5. IBS and composition select one approved catalogue generation, retain the Recipe/variant/layout and all exact revisions/checksums, associations, dependencies and actual Tool artifacts, then create the ephemeral BuildInstruction and prepared program references. Recipes hold stable UUIDs; selection supplies exact versions. Matching, assembly, child execution and continuation retain the same selection.
6. Keep intermediate results owned by the task in Monty. Validate each producer before a consumer reads it, preserve missing versus null, and propagate failures. Bindings grant no permission; the kernel checks live global Tool policy before dispatch. Missing support or an incompatible approved combination is an assembly error, never a No-Match or permission to downgrade.
7. Qualify the complete Recipe combination and production path. Planned layouts, associations, adapters and flow support must exist before activation. Example Python parsing does not establish Monty, behavior or bootstrap acceptance. Installation seeds use reviewed noncircular system_seed qualification; installed edits use authored Q1/behavior/human-Q2.

## 16. MCP exposes Skills and submits Python to the global orchestrator

The operator clarified the intended MCP contract: when enabled, connected models discover Orchestrator Skills as MCP “tools”, receive instructions for designing/formating supported Python, submit that Python in a tools/call request, and receive the formatted result after the already-running global orchestrator executes an isolated child task. Rust Tools remain behind the existing Python -> host -> Rust/kernel boundary. MCP is an external transport into this architecture; it is not a second execution engine or an endpoint that only returns assembled source.

The earlier “migrate or retire” suggestion applies to the obsolete handler/composer dependency, **not to removal of the MCP capability**. Replace it with this bridge. The source audit still stands: current tools/list projects Skills but only abbreviated descriptions/slot-derived schemas; tools/call expects arguments, resolves a Skill UUID, passes an empty Recipe step_link and does not run the result. The default listener is a no-op. Model-Python transport, child admission, execution and formatted completion are missing implementation/acceptance, not shipped behavior.

### Target sequence and responsibilities

1. **Discovery and instructions.** tools/list exports eligible approved Orchestrator Skills, with unambiguous external names mapped to stable Skill UUIDs and usable input/result/failure contracts. Each Skill's one-Tool prose, associated executable implementation and qualified binding supply its meaning; a Rust primitive/domain overview is not substituted. Supply the connected model with the supported Monty/Python authoring and result-format instructions and the actual invocation surface. Truncated descriptions/empty schemas cannot replace that contract. Listing grants no permission.
2. **Explicit Python submission.** tools/call identifies the listed usage and submits Python as deliberately authored source, with runtime inputs transported separately as typed data. Define a versioned request envelope/schema and client instructions before implementing it; current argument-to-key=value flattening is not that contract. Do not invent presently supported field names. No runtime values are interpolated into Python or inserted into approved component source.
3. **Admission into the global service.** The Rust MCP transport validates the envelope and hands the work to the existing durable admission/global orchestrator path. Pin the selected Skill/association/binding/Tool implementations and pure dependencies from one coherent approved generation at admission. The global orchestrator owns the child invocation, sequencing, waits and completion. Keep explicit external request/session, parent/child run and attempt IDs; no separate global Monty, per-client driver or Rust agent loop. A child means an isolated bounded execution context in this service, not necessarily another model/subagent or an OS VM.
4. **Python -> Rust execution.** Inspect/compile the submitted source against the exact pinned Monty and supported child-call semantics, with the actual selected host bindings. Expose only the usages/bindings established by the admitted request; no access to protected root ports or host registration by source text. Apply recursive argument/result contracts, technical sandbox/secret/network/resource constraints and current global Tool policy before every dispatch. The selected Skill normally remains one Tool usage. If submitted code needs several independent usages, require explicitly supported separate steps/bindings and retained data flow rather than concealing them in one Skill. Prose, a name or successful parse never grants execution authority.
5. **Formatted completion.** The global child validates the real Tool result and executes the specified reusable Python formatting, then the Rust bridge serializes that result into the MCP response. Formatters may be supplied/chosen under the declared transient-code or approved-component contract, but cannot erase failure/truncation/unknown effect state. Return actual completion/failure/wait through the supported protocol, rather than composed source or a success placeholder. MCP response delivery is this request's output; do not also post the result into an unrelated chat with N01 or append ordinary chat history with N02.

### Submitted source is not automatic component publication

Keep deliberately submitted model Python distinct from typed runtime input and from activated library PythonCode. The request does not install a Skill/Recipe/component revision, mutate the protected root, or receive system_seed provenance. Explicitly define and implement the transient code admission/inspection/execution contract; current retained execution accepts exact reviewed component source, so accepting external code is an adapter/continuation gap rather than an existing implicit feature. Record exact request source/checksum and retained dependencies with the task as required for audit/recovery. Never reuse a canonical class22 component's approval to certify a different submitted body just because it names the same Skill.

When the child reuses canonical approved Skill code, its actual exact association approval still applies to that unchanged code/combination. Any submitted wrapper or formatter has its own transient source identity and supported checks; a source parser alone does not prove arbitrary semantic equivalence. Do not advertise code as approved catalogue/Tier0 work from a mature label. Later installing a useful submitted pattern as library components follows the separate authored Q1/behavior/human-Q2 path; executing a transient request is not such an installation and must not invent a human-Q2 or fingerprinted invocation-approval requirement for every MCP call. Live global Tool policy remains independent.

Reuse the existing global owner, durable admission/attempt fencing, task isolation, source inspection, typed transport, registered Tool adapters and Skill association/approval machinery. Reuse the small Python components/formatters already in this plan when their exact contracts fit; MCP does not justify duplicate file/HTTP/JSON/shell executors or a specialized Rust workflow Tool. A supported explicit internal invocation Recipe can provide this reusable execution/formatting structure; its identity/layout/source-admission contract must be authored, not fabricated by passing a Skill UUID to a Recipe composer.

Implement the missing versioned model-code request contract, complete Skill instruction projection, collision-safe listing/call resolution, transient-source admission and isolated global child/result bridge. Rust owns MCP protocol/listener/authenticated instance access, transport, technical inspection and primitive dispatch; Python/global orchestration owns execution sequencing and semantic formatting. Enabling requires the real listener wiring and a functioning execution path. Disabled means no new MCP discovery/admission; in-flight handling must follow the documented cancel/drain contract. These infrastructure changes are prerequisite work, not additional class22 entries in the Python component list.

### Acceptance

- An enabled real listener lists Orchestrator Skills rather than Rust Tools; names are unique, and the model receives enough exact instructions/schema to write a valid supported Python request.

Listing/call races either resolve the explicitly accepted exact selection or return a clear contract/version error before effects; no silent latest rebinding.

- Concurrent external clients and ordinary chats stay isolated. Non-completed effects, disconnects, response-format/delivery failures and retried MCP requests preserve durable receipts and attempt counts; a lost response never automatically replays a completed write.
- A transient code execution does not create an activated component or inherit another body's review. A permanent successor can be authored separately through its required review path. The current no-op listener and source-returning handler cannot pass this acceptance matrix.

### Monty-specific implementation gates

The selected dependency is the local Rust [monty-control package](../../vendor/monty-control/BRASSCLAW.md): upstream v1.0.0 commit 85c5d1f6bef038405cfc40a4eed94806e303567e, extension 1.0.0-brassclaw.control.7 and dump ABI 0xBC04. Recheck these exact identities before implementation. Upstream Python/JavaScript session/pool examples do not establish that BrassClaw's retained adapter implements the same APIs. Monty is a Python interpreter; VM refers to that execution machinery. Upstream worker pools provide their own process APIs; BrassClaw does not inherit those APIs merely by using the Rust interpreter. The current [startup](../../crates/brassclaw_reborn_composition/src/global_monty_startup.rs) and [GlobalProcess](../../crates/brassclaw_monty_host/src/process.rs) host the global root in one privately spawned worker executable with framed IPC, a cleared environment and configured physical/frame backstops. That worker is an implementation isolation boundary, not a VM per task or proof of complete production recovery/settings/catalogue acceptance. The one global service/task isolation target is unchanged. See [Monty overview](https://pydantic.dev/docs/monty/).

BrassClaw's step-local inputs mapping, host.<tool> call surface and result capture are adapter contracts, not names automatically supplied by upstream Monty. Validate exact assembled code/declarations and its retained dependency graph under the selected engine. Optional type checking and stubs must reflect the real host interfaces; they supplement runtime recursive contracts and never establish behavior, approval or authority. Upstream eval/exec availability is distinct from BrassClaw's policy forbidding dynamic runtime source. Limit accepted modules/callables to the qualified component profile even where upstream offers more. See [host functions](https://pydantic.dev/docs/monty/concepts/host-functions/), [type checking](https://pydantic.dev/docs/monty/concepts/type-checking/), [limitations](https://pydantic.dev/docs/monty/limitations/) and [JSON limitations](https://pydantic.dev/docs/monty/limitations/json/).

Upstream eager iterators/generator expressions and interpreter allocations need finite admitted values and supported resource accounting. Feed/turn limits do not by themselves implement BrassClaw's cumulative executing-time account across steps/feeds/children/waits; preserve that account and effective setting revision, excluding idle/external waits. Interpreter allocation limits do not bound process RSS, compilation or host callback memory/work. Host callbacks need their own kernel/transport technical limits, cancellation and current global policy. An interpreter-terminal heap/time/control failure fences the affected global generation and enters supervised reconciled recovery; do not assume a damaged global heap can continue or silently spawn a per-chat replacement. See [resource limits](https://pydantic.dev/docs/monty/concepts/resource-limits/) and [security](https://pydantic.dev/docs/monty/concepts/security/), together with the local control extension's task-preemption/terminal-error contract.

Persisted Monty snapshot bytes are not inherently authenticated. Accept only a trusted producer/storage boundary with authenticated integrity and compatible exact engine/control ABI and retained workflow/state references; an attacker-controlled blob plus its checksum is insufficient. Never accept snapshots from model/MCP input or treat a restored callback/authority object as a grant. Restore controls/resource settings and trusted host objects through the qualified recovery owner, reconcile durable effects/counts and fence the old generation before supervised replacement. A heap dump is not a durable workflow checkpoint. See [snapshots](https://pydantic.dev/docs/monty/concepts/snapshots/).
