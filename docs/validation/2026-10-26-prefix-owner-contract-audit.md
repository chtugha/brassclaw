## Binding result

One reusable generation process produces a finished fixed prefix for its exact provider/model and role/task. Retain exact characters/UTF-8 identity. Generation, Kohai and Sempai when using that same provider/model pair consume the same stored accepted immutable design revision for the pair. That design owns compatible generation-time prefix format and runtime dynamic-prompt/join rules; no independent mutable Kohai formatter setting.

The corrected final request sequence is Orchestrator dynamic input, Kohai formatting ONLY that input with the stored accepted final-target design, optional connected Sempai optimization/correction of that already formatted prompt and return of the final dynamic prompt, then Kohai inserting the intended exact finished prefix unchanged once BEFORE the final dynamic prompt, final complete-request limits/policy check, and submission. Kohai does not format Sempai's return again. Sempai's own request independently uses its selected design/reviewer prefix and guard. The final provider prefix is not part of Sempai's editable payload. Wait/resume retains selected designs and prefix artifacts; another model or newer design cannot silently substitute.

The provider's default template applies without provider-host configuration access or a global role template override. A transport that would reformat the fixed prefix or move dynamic content ahead of it is not qualified for this join until repaired. Physical span diagnostics are not an alternate serving architecture; the configured prefix ceiling is not an LCP or a cache-residency promise.

The corrected implementing owner is [Prefix remaining steps6/7 and sections4.1/5.3/serving](../plans/prefix_v3_upgrade.md). The binding correction, six producer/package/consumer steps and final acceptance matrix explicitly include stored-design use and format-before-correction-before-insert. This audit adds no parallel implementation plan or owner. Shared selection/admission/policy support remains with Simplified; Recipe-owned Sempai semantics retain the existing v3.5 ownership.

## Actual code findings still requiring that migration

- V145 already stores immutable model specifications, proposals and acceptance records. `prefix_model_designs.rs` explicitly excludes acceptance/activation and returns `design_generation_available: false`. Its current callers manage declarations/diagnostics; a production reader that resolves accepted designs for Kohai's formatter is not implemented there. A database schema or saved proposal is not runtime design consumption.
- Ordinary skills-db startup in `runtime.rs` supplies InstalledMontyCatalogue as SystemBundleSource. Its run-scoped reader authenticates user/project/run and returns the retained task catalogue prefix. That is the existing scoped catalogue/inline-context boundary, not accepted model-specific generated-prefix/design serving. Preserve its applicable acceptance without broadening it.
- The actually wired InterceptingModelGateway captures an already assembled request/system basis before review, preserves protected system context in `recompose`, and constructs Sempai review from that request basis plus its persona. Exact-base preservation is useful existing infrastructure, but does not prove final provider prefix insertion AFTER correction or independent Sempai/final model-design binding. The owning migration must separate dynamic review input, both retained target selections/designs, dynamic formatter and exact final-prefix join without introducing a Rust workflow loop.
- PgKohaiPort is a separate legacy text interface: it loads a scoped bundle and constructs system/history/user messages and explicitly has no Sempai wired. Its directly inspected constructor use is a runtime unit test. Do not mistake its name/comments for the selected ordinary global model path or full architecture support.

There was no implementation of the withdrawn neutral-prefix/whole-prompt-render interpretation. The remaining gaps predate that plan wording; they are real open migration requirements, not newly accepted alternate architecture. Runtime conformance requires actual accepted-design read/use, independent two-target Sempai checks, event-order and exact-prefix byte assertions after edits/resume, full final-request measurements and zero submission on mismatches. These acceptance requirements belong to the linked owning steps.
