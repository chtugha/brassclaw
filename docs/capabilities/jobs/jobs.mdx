**Jobs** are units of work produced by the trigger system, routines, and direct
user messages. All jobs are admitted as tasks to the **global Monty
orchestrator** — a single VM that processes admitted work through the matched
Recipe execution path.

Concurrent job capacity is managed through the orchestrator's shared heap and
task admission limits, not through a pool of independent agent-loop instances.
Each job has isolated task context: its own pinned component snapshot, typed
inputs, and result state. No shared mutable state crosses job boundaries.

---

## Job state

Each job is tracked through the following states:

```
pending
    ↓
running ────────────────────┬──► completed
    ↑                        │
    │  (repair attempt)       └──► failed
    │
  stuck ──────────────────────► failed (repair limit reached)
```

| State | Description | Next states |
|-------|-------------|-------------|
| `pending` | Created, queued for orchestrator admission | `running` |
| `running` | Actively executing in the orchestrator | `completed`, `failed`, `stuck` |
| `completed` | Finished successfully | — (terminal) |
| `failed` | Unrecoverable error or explicit cancellation | — (terminal) |
| `stuck` | No progress within the configured timeout | `running` (repair), `failed` |

State and audit records are stored in the `agent_jobs` table (`stuck_since`,
`repair_attempts`, `started_at`, `completed_at`). Each job's tool call history
is stored in `job_actions`.

---

## Tool-failure tracking and repair

The `tool_failures` table records repeated execution failures per tool name
across jobs. This data is used by the self-repair system to assess recovery
feasibility and inform retry decisions. See [Self-Repair](/capabilities/jobs/self-repair).

---

## Parallel execution

Multiple jobs can be admitted and run concurrently. Concurrency is bounded by
the orchestrator's shared heap allocation and task scheduling capacity. Each
running job occupies its own isolated execution context within the single global
Monty VM.

When the orchestrator is at capacity, new jobs queue in the `pending` state
until a running job completes or a slot becomes available.

## Job-management tools

Four first-party tools let the agent interact with jobs at runtime:

| Tool | Description |
|------|-------------|
| `create_job` | Create a new job with a description and optional context |
| `list_jobs` | List active jobs with their current state and metadata |
| `job_status` | Get detailed status for a specific job by ID |
| `cancel_job` | Cancel a running or pending job |

These are class-0 Rust primitives registered through `builtin_bootstrap.rs`,
each backed by a ToolSkill, PythonCode, Skill, and Recipe component stack in
the standard v3 pattern.

## Execution time limits

The default task compute time limit is **600 seconds of executing VM time**,
excluding idle time, queue waits, and external waits (e.g., awaiting a tool
response from an external service). This limit applies to the job's active
execution time, not its total wall-clock lifetime.

The limit is configured via **Settings → Monty VM** → task duration. It governs
individual task execution, not the global orchestrator's lifetime.
