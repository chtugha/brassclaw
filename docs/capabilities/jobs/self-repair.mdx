BrassClaw monitors running jobs and attempts recovery when a job stops
producing output or tool call activity for longer than the configured timeout.

---

## What makes a job stuck?

A job is classified as **stuck** when it has been in the `running` state for
longer than the configured inactivity threshold without recording any new tool
call activity, output, or state update in `job_actions`.

Common causes:
- LLM provider timeout or rate limit with no retry budget remaining
- Tool call hanging on an unresponsive external service
- Resource exhaustion at the orchestrator or host level
- Network partition between the orchestrator and a sandboxed subprocess

---

## Detection

The self-repair monitor runs as a background task. It periodically scans all
running jobs and compares the last-activity timestamp in `job_actions` against
the stuck threshold.

```
[Self-Repair Monitor]
         ↓
For each running job:
    last_activity > stuck threshold?
         ↓ yes
    Mark job stuck (set stuck_since)
         ↓
    Record in tool_failures table
         ↓
    Evaluate recovery eligibility
```

The `tool_failures` table accumulates failure records per tool name. The repair
system checks this history to determine whether the job has exceeded its retry
budget.

---

## Recovery

When a stuck job is detected:

<Steps>
  <Step title="Mark stuck">
    The job's `stuck_since` timestamp is set. The event is logged.
  </Step>

  <Step title="Check repair budget">
    The system reads `repair_attempts` on the `agent_jobs` row. If the job has
    reached the maximum, it transitions directly to `failed`.
  </Step>

  <Step title="Re-admit">
    If retries remain, `repair_attempts` is incremented and the job is returned
    to the `running` state. The task is re-admitted to the orchestrator.
  </Step>

  <Step title="Evaluate outcome">
    If the job completes successfully, it reaches `completed`. If it gets
    stuck again, the cycle repeats until the repair limit is reached.
  </Step>
</Steps>

<Warning>
Re-admitting a job does **not** replay its already-completed Tool calls.
The orchestrator uses durable effect state to identify where execution was
interrupted. Completed Tool invocations are not reissued — only unstarted or
verifiably incomplete steps are resumed. A job whose last Tool call produced
an unknown completion outcome (e.g. a timeout after an external write) is
stopped and classified as failed rather than replayed automatically.
</Warning>

## Tool-failure history

Every tool call failure during job execution is recorded in `tool_failures`:

| Field | Description |
|-------|-------------|
| `tool_name` | Which tool failed |
| `error_message` | Error reason |
| `error_count` | Cumulative failure count for this tool name |
| `last_failure` | Timestamp of most recent failure |
| `repair_attempts` | How many repair attempts have been made |
| `repaired_at` | Timestamp when the tool was last considered repaired |

The repair monitor uses `error_count` and `repair_attempts` to decide whether
re-admission is appropriate. A tool that fails on every attempt across all
repair tries contributes to moving the job to `failed`.

---

## Configuration

Stuck detection and repair thresholds are tracked per-job in the `agent_jobs`
table (`stuck_since`, `repair_attempts`) and per-tool in `tool_failures`
(`error_count`, `repair_attempts`). The monitor's check frequency and the
stuck inactivity threshold are runtime parameters of the self-repair subsystem.

<Note>
The specific Settings → UI path for adjusting stuck detection timeout,
maximum repair attempts, and monitor check interval is implementation-pending.
Confirm the current control surface via Settings → Monty VM before relying on
a specific knob location.
</Note>

Regardless of how repair thresholds are configured, the hard task-duration
limit (Settings → Monty VM → task duration, default 600 s executing VM time)
is independent: it terminates a task regardless of repair state when the
execution-time ceiling is reached.

## Observability

- **`list_jobs` tool** — Shows current job state including `stuck` jobs
- **`job_status` tool** — Detailed per-job state including `stuck_since` and
  `repair_attempts`
- **Logs** — Enable debug logging for the repair subsystem to see detailed
  stuck detection and re-admission events

## Troubleshooting

<AccordionGroup>
  <Accordion title="Job repeatedly gets stuck" icon="refresh-cw">
    - Use `job_status` to inspect `stuck_since` and `repair_attempts`
    - Check tool failure records for the specific failing tool
    - Verify network connectivity to LLM provider and external services
    - If the job is legitimately long-running, increase the stuck detection
      timeout via Settings → Monty VM
  </Accordion>

  <Accordion title="Job fails immediately after recovery" icon="x-circle">
    - Tool failure history may show a specific tool that consistently fails
    - Check whether the external service the tool depends on is available
    - Review the job's `job_actions` history for the last recorded activity
  </Accordion>

  <Accordion title="Stuck jobs not being detected" icon="search">
    - Verify the self-repair monitor is running (check startup logs)
    - Check that the stuck detection timeout is not set unreasonably high
    - Confirm the job is actually in `running` state via `list_jobs`
  </Accordion>
</AccordionGroup>
