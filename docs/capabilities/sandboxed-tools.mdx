BrassClaw tools run as **registered Rust primitives** (class-0 components) or
as **extension capabilities** backed by one of two runtime lanes:
**First-party** (host-owned Rust code) or **Hosted MCP** (external MCP server
with host-mediated egress). The WASM/wasmtime sandbox and Docker-script lanes
were removed in Phase 4 of the v2 consolidation.

<Note>
The old `sandboxed-tools` WASM model no longer exists. If you have existing
documentation or tooling referring to `capabilities.json`, `wasmtime` fuel,
or `workspace_read`/`workspace_write` WASM host functions, those belong to
the removed subsystem. See the [Extension guide](/extensions/building-a-tool)
for current patterns.
</Note>

---

## Runtime lanes

Every extension tool declares exactly one runtime lane in its `manifest.toml`:

| Lane | Use when | Examples |
|------|----------|---------|
| `first_party` | Logic is host-owned — a Rust crate shipped with the binary | Internal HTTP wrappers, cron, memory tools, file tools |
| `mcp` | Provider already exposes an MCP server; host locks egress to that endpoint | Notion, GitHub hosted MCP |
| `system` | Host-owned system fixtures — not user-installable | Regression test fixtures and reference implementations |

The `wasm` and `script` lanes are no longer wired. Do not use them.

## Capability declaration

Every model-visible tool capability is declared in the extension manifest via
`[[host_api]]` with `brassclaw.capability_provider/v1`:

```toml
schema_version = "reborn.extension_manifest.v2"
id = "my-tool"
name = "My Tool"
version = "0.1.0"
description = "Fetches data from example.com"
trust = "third_party"

[runtime]
kind = "mcp"
transport = "stdio"
command = "my-mcp-server"
args = ["--stdio"]

[[host_api]]
id = "brassclaw.capability_provider/v1"
section = "capability_provider.tools"

[capability_provider.tools]

[[capability_provider.tools.capabilities]]
id = "my-tool.search"
description = "Search records in example.com"
effects = ["dispatch_capability", "network", "use_secret"]
default_permission = "ask"
visibility = "model"
input_schema_ref  = "schemas/my-tool/search.input.v1.json"
output_schema_ref = "schemas/my-tool/search.output.v1.json"
prompt_doc_ref    = "prompts/my-tool/search.md"
required_host_ports = ["host.runtime.http_egress"]
runtime_credentials = [
  { handle = "my_api_key", source = { type = "product_auth_account", provider = "my-tool" },
    audience = { scheme = "https", host_pattern = "api.example.com" },
    target = { type = "header", name = "authorization", prefix = "Bearer " } },
]
```

## Network and credentials

All network access is **host-mediated**. Runtime code does not create its own
HTTP clients or read raw secrets.

- **Hosted MCP** — requests go through `McpHostHttpClient` with
  `McpRuntimeHttpAdapter` and a host-owned egress planner.
- **First-party** — calls `brassclaw_host_runtime` HTTP helpers directly.

Credentials listed in `runtime_credentials` are never passed into the runtime
as raw token values. The host egress layer intercepts each outbound request and
injects the declared credential header before forwarding. The runtime module
never sees the raw secret material.

Network policy (allowed hosts, TLS enforcement, credential scoping) is enforced
at the host layer:
- Hosted MCP policy: `crates/brassclaw_reborn_composition/src/mcp.rs`
- Host HTTP enforcement: `crates/brassclaw_host_runtime/src/egress/`

## Effects and permissions

`effects` in the capability declaration are authorization inputs, not
documentation labels:

| Effect | When to include |
|--------|-----------------|
| `dispatch_capability` | Always for a dispatchable capability |
| `network` | Any external HTTP/TCP call |
| `use_secret` | Any credential injection (including product auth accounts) |
| `external_write` | Provider mutations, sends, deletes, workflow dispatches |
| `read_filesystem` | Local file reads |
| `write_filesystem` / `delete_filesystem` | Local file writes or deletes |
| `execute_code` / `spawn_process` | Process execution |
| `financial` | Irreversible financial actions |

`default_permission = "ask"` is the standard for anything with `external_write`,
`financial`, local write/delete, or process execution.

## Resource limits

Resource limits are enforced by the host runtime and Monty VM settings, not
per-capability configuration files:

| Limit | Control |
|-------|---------|
| Task compute time | **Settings → Monty VM** → task duration (default: 600 seconds of executing VM time, excluding idle/queue/external waits) |
| Shared heap | **Settings → Monty VM** → shared heap (minimum 512 MiB; ceiling, not reserved) |
| HTTP response size | **Settings → Monty VM** → host HTTP defaults (default 10 MiB) |
| HTTP request timeout | **Settings → Monty VM** → host HTTP defaults (default 30 s) |
| HTTP client retention | **Settings → Monty VM** → retained clients (default 128) |

## Discovery and installation

Extensions are discovered from `crates/brassclaw_first_party_extensions/assets/`
for built-in packages and from the virtual filesystem for operator-installed
packages. Every extension goes through:

1. Manifest schema validation (`brassclaw_extensions::v2::validate`)
2. Host-API contract parsing
3. Effect/credential consistency check
4. Trust ceiling check
5. Schema and prompt reference resolution
6. Runtime adapter health probe (for hosted MCP lanes)
7. Catalogue publication into the prompt-envelope tool surface

A failure at any step rejects the extension at install time. There is no
partial-load path.

## First-party tools

Built-in tools (memory, file, shell, HTTP, JSON, etc.) are registered as
class-0 Rust primitives through `builtin_bootstrap.rs`. They are not extension
packages — they are part of the system. Each has:

- A **Tool** row (class 0) identifying the primitive and its `capability_id`
- A **ToolSkill** row (class 13) describing the IBS binding
- One or more **PythonCode** rows (class 22) implementing specific usages
- **Skill** rows (class 1–3) associating prose with each PythonCode usage
- **Recipe** rows (class 21) providing the matched workflow

The current first-party tool inventory includes: `read_file`, `write_file`,
`shell`, `json`, `http_get`, `http_post`, `memory_search`, `memory_write`,
`memory_read`, `memory_tree`, `post_reply`, and others. See the
[Extension overview](/extensions/overview) for the full surfaced catalog.
