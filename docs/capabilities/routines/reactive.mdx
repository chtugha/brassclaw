---
title: Reactive Routines
description: Event-driven and webhook-triggered automation
---

Reactive routines fire in response to events rather than a schedule. They
automate workflows that should happen when something occurs — a memory document
is written, a webhook fires, or an internal job event is raised.

Like all routines, reactive triggers submit admitted tasks through the ordinary
trusted trigger ingress. The orchestrator receives them as normal tasks and
executes the matched Recipe workflow.

---

## Trigger types

### Event triggers

Internal events that reactive routines can listen for:

| Event | When it fires |
|-------|---------------|
| `job.completed` | Any job finishes successfully |
| `job.failed` | Any job reaches the `failed` state |
| `memory.write` | A memory document is created or updated |
| `routine.run` | Another routine completes a run |
| `heartbeat` | The heartbeat routine fires |

Event triggers support JSONB `trigger_config` for filtering. For example, a
routine that listens for writes to a specific memory path prefix:

```json
{
  "event": "memory.write",
  "filter": {
    "path_prefix": "inbox/"
  }
}
```

### Webhook triggers

Reactive routines can be triggered via an HTTP endpoint. When a webhook trigger
fires, the request body is available to the action as context.

```json
{
  "type": "webhook",
  "path": "/hooks/deploy-complete"
}
```

The endpoint is exposed at:

```
POST https://<your-brassclaw-host>/hooks/<path>
Authorization: Bearer <webhook-secret>
```

The webhook secret is stored in the encrypted secrets store. Webhook trigger
endpoints are managed via **Settings → Routines** or the `routine_create` tool.

<Note>
Webhook trigger endpoint management is not yet exposed in the WebUI. Create
webhook routines via the `routine_create` tool until UI support is added.
</Note>

### Triggering from a CI/CD pipeline

```bash
curl -X POST https://brassclaw.example.com/hooks/deploy-complete \
  -H "Authorization: Bearer ${DEPLOY_WEBHOOK_SECRET}" \
  -H "Content-Type: application/json" \
  -d '{
    "environment": "production",
    "version": "v1.4.2",
    "commit": "abc1234"
  }'
```

The request body is passed as context to the action prompt.

## Routine guardrails

Reactive routines support per-routine resource limits declared in `action_config`:

| Field | Description |
|-------|-------------|
| `max_tokens` | Maximum LLM tokens for the run |
| `max_tool_calls` | Maximum tool calls before the run stops |
| `allowed_tools` | Allowlist of tool names the action may use |
| `timeout_secs` | Hard run timeout in seconds |

Rate limiting is declared in the routine's `trigger_config`:

```json
{
  "rate_limit": {
    "max_runs": 10,
    "window_secs": 3600
  }
}
```

<Warning>
Always set `rate_limit` on webhook-triggered routines. Without it, a
misconfigured external service flooding your endpoint will spawn admission
requests at unbounded rate.
</Warning>

Per-routine `allowed_tools` restricts the action's tool use for that specific
routine. This is distinct from the instance-wide Tool policy (Settings →
Tool Permissions), which applies to all tasks globally. Both apply — a tool
blocked by instance-wide policy cannot be unlocked by a routine allowlist.

## Deduplication and cooldown

Reactive routines can be configured to prevent rapid-fire execution:

| Field | Description |
|-------|-------------|
| `cooldown_secs` | Minimum seconds between consecutive runs (default: 300) |
| `dedup_window_secs` | Optional window during which identical triggers are deduplicated |
| `max_concurrent` | Maximum simultaneous runs of this routine (default: 1) |

The trigger poller validates these constraints before submitting a trigger
event. A trigger that fires during a cooldown or dedup window is silently
dropped.

## Execution context

Reactive routine jobs receive the triggering event payload as context. For
webhook triggers, this includes the request body. For event triggers, this
includes the event metadata (job ID, memory path, etc.).

The action prompt can reference context fields:

```
action: "A deployment just completed: check the version,
         run smoke tests, and write a summary to memory
         at ops/deployments/<date>.md"
```

Context data is passed as typed inputs through the routine's action Recipe.
It is never interpolated as Python source.
