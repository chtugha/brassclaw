Use **Settings → Inference** to manage provider definitions, credentials and
model selections. BrassClaw stores these values in PostgreSQL and resolves
startup, model discovery and live reload from that catalogue. Provider files
and LLM environment variables do not override a selected database definition.

## Configure inference

1. Open **Settings → Inference** with your instance operator session.
2. Add or edit a provider. Choose its protocol, endpoint and model; provide any
   required credential through the credential field.
3. Test the provider connection or load its available models. Discovery uses
   the provider's selected endpoint, credential and technical limits.
4. Select the provider and model for the primary role, and configure Sempai
   separately when you enable post-turn review.

A provider's stable identifier is independent of its protocol. Changing its
name does not change the protocol adapter. Credentials are stored through the
encrypted secret store, not as plaintext provider-definition values.

Removing a provider hides and deactivates its retained definition. Use
**Add provider** to restore it explicitly. Restoration does not reinstate an
old role selection automatically. Startup preserves operator edits and removed
providers; it does not synchronize them against a bundled provider file.

## Provider technical settings

Each provider dialog explains these fields next to their controls:

| Setting | Meaning |
| --- | --- |
| Request timeout | Maximum time for an individual provider HTTP request. A retained in-flight client keeps its selected deadline. |
| Additional retries | Attempts after the initial request, for eligible transient failures. Permanent rejection and authentication failures do not become successful replies. |
| Retry delay and jitter | Initial delay, maximum exponential backoff and random variation between retries. |
| Provider-hint ceiling | Maximum wait taken from a provider's retry-after hint. |
| Circuit threshold and recovery | Repeated failures can temporarily stop requests to that client; recovery controls when it may probe again. Zero threshold disables the circuit. |
| Response bytes | Optional model-response ceiling. Zero in the form disables this ceiling; a finite overflow fails without a successful truncated answer. Unsupported finite transport limits are rejected. |
| Discovery timeout and bytes | Limits for fetching model metadata. Discovery failure does not fabricate a model list. |
| Completed-response cache | Enable retention, set maximum entries and lifetime. Zero capacity or lifetime disables retention. This is separate from provider prompt caching. |

Settings changes use revision checks. If another edit wins first, reload the
current values and apply your change again. A saved value and acknowledged
runtime uptake are separate states; inspect the reported uptake status when
changing an active role.

## Monty runtime settings

Use **Settings → Monty VM** for task compute time, the shared heap and execution
boundary capacities. The task duration counts executing VM time, excluding
queue and external waits. It does not limit the global orchestrator's lifetime.

The shared heap defaults to sizing once at startup and remains constant.
Startup/manual values have a 512 MiB minimum. This value is a ceiling, not a
reservation. Larger finite values can be changed live; an unsafe manual
reduction is rejected. Automatic sizing is optional, and mild pressure alone
does not pause all admission.

Token budgets default to disabled. Accounting remains visible, and actual
model context/output constraints still apply. Enabling task token budgets is
separate from task time and heap settings.

Host HTTP client retention is also an execution setting. Its default is 128
reusable clients; zero disables retention. Least-recent clients are evicted
individually, while active requests keep their handles. This setting controls
host-mediated Tool/extension HTTP transport, separately from the model-response
cache in Inference settings.

Host HTTP defaults are also available here: request timeout in milliseconds
(default 30,000) and response size in bytes (default 10 MiB). They apply when a
host HTTP request omits an explicit bound. They are separate from model-provider
limits. New requests use acknowledged settings; requests already accepted keep
their captured limits. Values must be positive and representable on the host.
The first-party HTTP Tools inherit these values when the corresponding bound is
omitted. Explicit positive bounds are used exactly. Oversized responses fail;
complete sanitized text, binary data and headers are returned without formatting
truncation. Saved responses additionally require permission for the chosen path.

## Bootstrap and upgrades

Bootstrap configuration locates the instance home and PostgreSQL connection.
It does not supply an alternate provider catalogue. Keep external-service
credentials in their supported authentication boundary.

The explicit legacy migration command can import supported old operator files,
including provider definitions and role settings. It retains the source and a
content-addressed backup, reports conflicts with newer database values, and
rolls back a failed import transaction. These files are upgrade inputs, never
an active startup fallback.

Dedicated OAuth/signed setup metadata and cross-platform acceptance are still
being completed in the v3 implementation. Use the supported configuration
controls and consult release acceptance before relying on those paths.
