## Step 1 — Update AGENTS.md: Rule 3 carve-out for dependent sequential chains

**Why this comes first:** The entire architectural correction of the plan
(splitting one monolithic Rust tool into two primitives chained in one
PythonCode body) requires AGENTS.md Rule 3 to be updated to allow it.
If Rule 3 is not updated first, the v10 plan itself violates the rule as
written. The rule update is the foundation everything else builds on.

**Finding addressed:** Finding 23 (Rule 3 contradiction).

**Current AGENTS.md Rule 3 text (in `## Orchestrator-First, LLM-Minimal Design` section):**

> **Rule 3**: One PythonCode executor block = exactly one `__execute_action__()` call.
> Multiple dispatches require multiple PythonCode blocks — one per tool call.

**Problem:** The retired `__execute_action__` meta-primitive is gone. The rule
translates to "one `host.<tool>(...)` call per PythonCode body." But there is a
legitimate case: a **dependent sequential chain** where tool B's input is tool A's
output, and they cannot be separated without cross-step isolation. Merging them
into one Rust tool just to satisfy Rule 3 is the wrong solution — it embeds
sequencing logic into Rust (violating the Orchestrator-First principle) and
eliminates reusability of both primitives.

**Edit to make in `AGENTS.md`:**

Locate the paragraph containing "Rule 3" (in the `### Q1 Hard Errors` section).
Replace the current Rule 3 text with the following expanded version:

```
- **Rule 3**: One PythonCode executor block = exactly one independent `host.<tool>(...)` call.
  Multiple **independent** dispatches (tool A and tool B are separately useful, their outputs
  do not flow directly into each other) require separate PythonCode blocks — one per tool call.

  **Exception — dependent sequential chain:** If tool B's input is the direct runtime output
  of tool A (B literally cannot run without A's result), both calls may share one PythonCode
  body. This is valid because they execute in a single `host.run_program` context and share
  local scope. The pair must form a single logical unit (e.g. sweep → store, read → transform).
  Example:
  ```python
  bundle_parts = host.sweep_validated_components(user_id="{{vars.slot0}}", project_id="{{vars.slot1}}")
  result = host.store_prefix_bundle(
      user_id="{{vars.slot0}}", project_id="{{vars.slot1}}",
      bundle=bundle_parts["bundle"]
  )
  ```
  Two `host.*` calls, one body — valid because `bundle_parts["bundle"]` is the direct input to
  the store call. Do **not** use this exception to bundle unrelated tool calls for convenience.
```

**Verify after editing:** The rule now clearly distinguishes independent dispatches (must be
separate bodies) from dependent chains (may share one body). The sweep→store pattern is
explicitly covered as the canonical example.

## Step 2 — Update CLAUDE.md: Recipe-first principle enforcement

**Why:** The audit found no explicit CLAUDE.md text that addresses the "merge into Rust to
solve cross-step isolation" anti-pattern. The `include_str!` rule also needs a note about
the `builtin_bootstrap.rs` constant pattern for non-prompt files.

**Findings addressed:** Findings 1, 2, 8 (the `include_str!` prohibition scope).

### Step 2-A — Add "cross-step isolation" anti-pattern warning to §Orchestrator-First

In CLAUDE.md, locate the `#### Turn Execution Flow` section. After the **Key points for
authoring** bullet list (ending `"Tier 0: no LLM … Tier 2: LLM over full base-prompt"`),
add a new callout block:

```markdown
> **Anti-pattern — do not merge primitives into Rust to solve cross-step isolation:**
> The step isolation invariant (each `host.run_program` call gets a fresh empty state)
> is not a reason to merge two independent operations into a single monolithic Rust tool.
> If tool B needs tool A's output, place both calls in **one PythonCode body** (they share
> local scope within one `host.run_program` execution). Only combine into one Rust tool if
> the operations are genuinely inseparable at the system level (e.g. an atomic DB transaction
> that cannot be split). Convenience and data flow alone do not justify a new monolithic tool.
```

### Step 2-B — Clarify `include_str!` rule to cover non-prompt reference files

In CLAUDE.md §Code Style, the current `include_str!` rule reads:

> **Do not introduce new `include_str!()` constants for behavioural prompts or scripts in
> production code paths.** … `include_str!()` is only permitted in `builtin_bootstrap.rs`
> seed constants and in `#[cfg(test)]` modules.

This covers prompts and scripts but is silent about reference/documentation files
(CLAUDE.md, AGENTS.md, etc.) that are embedded for bundle assembly. Add the following
sentence at the end of that rule paragraph:

```
This also applies to reference documentation files embedded for runtime use (e.g. CLAUDE.md,
AGENTS.md): if such a file must be included at compile time, its `include_str!()` constant
belongs in `builtin_bootstrap.rs` as a `pub(crate) const`, not in any other production file.
The backend or handler that uses the constant imports it as
`crate::builtin_bootstrap::SOME_CONST`.
```

## Step 3 — Rewrite prefix_plan2.md §Goal, §Ground Truth, and §New Flow

*This is the highest-impact rewrite. It corrects the fundamental architectural error in v9
(one monolithic Rust tool) and replaces it with the correct design (two Rust primitives +
one PythonCode body).*

**Findings addressed:** 1, 2, 3, 4, 5, 6, 27.

### Step 3-A — Rewrite §Goal

Replace Goal #5 entirely. The new text:

```markdown
5. **Two Rust primitives, chained in one PythonCode body.**
   `host.sweep_validated_components` (DB sweep + format) and
   `host.store_prefix_bundle` (persist to `PgBasicPromptStore`) are two separate
   Rust tools — each reusable independently by other recipes. They are chained
   in a single PythonCode executor body (`pc-host-assemble-prefix-bundle`) so
   that the `bundle` string produced by the sweep is directly passed to the
   store call within the same `host.run_program` execution context. No cross-step
   variable dependency; both calls share local scope inside one orchestrator step.
   See the Rule 3 carve-out in AGENTS.md (dependent sequential chain exception).
```

Also update Goal #3 to say "two focused Rust tools" instead of "one focused Rust tool."

### Step 3-B — Rewrite §Ground Truth: "Rust is just providing tools" subsection

The current text at lines 68–76 reads:

> "Rust is just providing tools … the sweep result must be immediately passed to the
> store call, both operations belong in one Rust tool."

Replace with:

```markdown
### Rust provides primitives; the orchestrator sequences them

The orchestrator is the execution engine. Rust provides **primitives** — the smallest
independently useful operations. A Rust tool must not contain sequencing logic; it
executes one operation and returns a result.

For the prefix bundle:
- `host.sweep_validated_components` sweeps all validated component tables, formats
  the bundle string, and returns `{bundle: String, component_count: usize}`.
- `host.store_prefix_bundle` takes a pre-assembled bundle string and stores it in
  `PgBasicPromptStore`, returning `{fingerprint, generation_ms}`.

These two tools are logically separate — the sweep can be called without storing,
and the store can be called with a bundle assembled by any means. They are chained
in **one PythonCode body** because the store call's `bundle` parameter is the direct
runtime output of the sweep call. A single `host.run_program` execution runs both
calls in one Python scope, so `bundle_parts` is available when `host.store_prefix_bundle`
is called. This satisfies the isolation invariant (no cross-step sharing) while keeping
both tools independently reusable.
```
