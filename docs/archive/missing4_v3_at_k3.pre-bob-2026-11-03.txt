## 2. Exact current state of the infrastructure

### 2.1 What exists (re-used for this work)

- **Eight legacy `validator-class-N` Recipes** in `reborn_recipes` with
  `validation_status = 'validated'` and `consumer_tags = ["05:validator"]`.
  These are mutable rows; they are *not* the retained-path revisions.

- **Eight `ComponentRevisionDraft` envelopes** in `reborn_component_revisions`,
  one per class, produced by
  `brassclaw_skills::validator_components::structural_validator_recipe_drafts`.
  Each envelope carries a `validator_coverage` field used by
  `RetainedValidatorCoverage::from_inputs()`. These have class-specific PC bodies
  and boot-time `pure-component-approval/1` records.

  *Note: `find_validator_recipe` currently reads from `reborn_recipes` (the
  `validates_class_code` column on legacy mutable rows — `pg_recipe_store.rs`
  lines 153–154). The `ComponentRevisionDraft` envelopes in
  `reborn_component_revisions` are produced but not yet read by the validator
  path — that wiring is the deliverable of Step 10-A.*

- **Six class-specific PC body constants** in `builtin_bootstrap.rs`:
  `PC_VALIDATOR_CLASS_0_BODY`, `PC_VALIDATOR_CLASS_SKILL_BODY` (classes 1–3),
  `PC_VALIDATOR_CLASS_13_BODY`, `PC_VALIDATOR_CLASS_21_BODY`,
  `PC_VALIDATOR_CLASS_22_BODY`, `PC_VALIDATOR_CLASS_23_BODY`.
  Selected via `validator_pc_body_for_class(class_code)`. Each body parses
  `inputs["content"]` as JSON (the component's content/steps field) and returns
  `{"pass": bool, "errors": [str]}`. Uses `import json` only; zero host calls.

- **16 fixture tests** in `validator_pc_body_tests.rs` (source-authored,
  live receipt pending TASK-022): two per class (valid + class-specific defect),
  run through `UtilityRequest::Evaluate` against the real Monty worker.

- **`bootstrap_validator_approval.rs`** — boot-time qualification for all eight
  validator PCs. Called from `component_boot.rs` after `qualify_all` (L013–L101).
  For each PC: reads the `ComponentRevisionDraft` from `reborn_component_revisions`,
  reads PC source content from `reborn_python_code` rows (via the UUID references
  in the draft) to compute checksums for the `PureComponentApprovalDeclaration`,
  writes Q1 evidence via `bootstrap_evidence::retain_intent`, writes behavioral
  evidence via direct `reborn_component_review_evidence` INSERT, then writes a
  `pure-component-approval/1` record via `record_pure_component_approval`.
  All UUIDs are deterministic (UUID v5, `VALIDATOR_QUAL_NAMESPACE`). Idempotent.

- **`run_q1_validation_retained`** — sole production Q1 entry point, wired via
  `ValidatorTaskDriver` → `GlobalMontyDriver::drive_admitted`. Legacy path removed
  (PKG-H). TASK-022 retest in progress.

- **`pg_retained_q1.rs`** — structural observation writer.

- **`pg_validator_q1_evidence.rs`** — durable Q1 evidence writer, links completed
  validator Recipe executions to `reborn_component_review_evidence` rows atomically.

- **`pg_association_review.rs`** — human Q2 route for one Tool-usage pair (one
  Skill + PythonCode). Existing scope: `catalogue_activated = false`.

- **`pure-component-review.md` exact remaining cutover contract** — eight-item
  requirement list for Steps 3/8–10. Items 1–8 are all open.

### Step 9 — Human Q2 path for authored (non-seed) validator changes

**Owner:** `crates/brassclaw_reborn_composition/src/pg_association_review.rs`,
`crates/brassclaw_product_workflow/src/settings.rs`,
`crates/brassclaw_webui_v2_static/…/settings-tabs.js`.

Step 9 of `validator_v3.md` requires that *installed authored changes* to
validator Recipes or their PythonCode go through authenticated human Q2.
The existing association-review panel covers only one Tool-usage (class-1 Skill)
pair. It must be extended to cover class-21 (Recipe) and class-22 (PythonCode-only)
review subjects.

**Extension approach:**

The existing `pg_association_review.rs` module uses `prepare_human_association_review`
/ `record_human_association_approval`, which are scoped to Skill+PythonCode pairs
and write `skill-association-approval/1` records. For class-21 (Recipe) and
class-22 (pure-logic PythonCode), **these functions cannot be reused as-is** —
they operate on a `skill_id` and write the wrong approval format. The correct
approach is to add **separate store functions** for Recipe and pure-logic Q2
that are reached through the existing class-code dispatch point in the
operator-only review handler:

- For class-22 pure-logic subjects: a new store function calls
  `record_pure_component_approval` after evidence verification.
- For class-21 Recipe subjects: a comparable new writer for Recipe workflow
  approval (which does not use `skill-association-approval/1`).

Do not create separately named API routes; the submission ID and review action
remain the same surface. The class code determines which store functions and
approval tables are written. Both paths require the G-5 migration before they
can store evidence in the correct format.

**Required work:**

1. Author and apply the G-5 migration (a checked successor migration to
   `reborn_component_review_evidence` per `pure-component-review.md` item 1)
   before any Step 9 evidence is written. Inspect the current migration
   inventory before allocating a version; never edit applied migrations.

2. Add separate store functions for class-21 and class-22 Q2 behind the
   existing class-code dispatch in the operator-only review handler. For
   class-22 pure-logic subjects, the approval path writes a
   `pure-component-approval/1` record (via
   `pg_pure_component_approval::record_pure_component_approval`), not a
   `skill-association-approval/1` record. Use `reborn_pure_evidence_submission_links`
   (V201) to bind each `submission_id` to its `approval_id`
   (`pg_pure_component_approval.rs` lines 298–310).

3. The review view must show the *reviewed combination* — draft revision +
   evidence records keyed to the exact submission ID — not a display recomputed
   from latest mutable rows. This applies to WebUI component detail and the
   validation-queue view.

4. Gate the approval write on: Q1 evidence exists and checksum matches, at
   least one behavioral evidence record exists and checksum matches, no
   partial/missing required checks. These gates require the G-5 migration to
   be in place; the existing V102/V106 schema cannot enforce them for pure/Recipe
   evidence. Enforce server-side without bypassing existing guards.

5. Also trace and verify that model/component-management ports (e.g. Sempai
   proposal sink, WebUI Recipes facade) cannot reach the Q2 write path — per
   `validator_v3.md §Step 9` item 4. A literal `human` field in the API body
   is not proof of authenticated action; use the existing `simplified Phase 1`
   ingress unchanged.

6. Authored Q2 applies only to installed changes; shipped packages use the
   existing `system_seed` path with `q2_ref = null`. The `bootstrap_validator_approval`
   module (Step 8) already handles the system-seed path correctly; do not
   modify it.

**Exact boundaries from `validator_v3.md` §Step 9:**
- Human review verifies semantics, coverage and the selected Q1/behavior records.
- Immutable human evidence and association approvals are written through trusted
  writers using `skills.md` formats unchanged.
- Required reused dependencies retain individual approvals; the new combination
  gets its own evidence.
- Extend linked review storage and readers explicitly where V102 usage-specific
  contracts do not suffice (`pure-component-review.md` items 1 and 6 give the
  exact migration requirement: introduce a checked successor migration, not a
  relabelling). Do not pretend class-21 or class-22 roots own a
  `skill-association/1`.
- Do not introduce a new outbox, queue framework or polling loop; bind submissions
  into the **existing shared review-runtime contract** (`simplified_v3.md`).
  Simplified implements request/run idempotency, wake/reconciliation and execution
  ownership; this step supplies exact submission/subject/validator/check-set
  references only.

**Acceptance:**
- A test authored Recipe change submitted via WebUI/API goes through:
  `submitted → Q1 pass → behavioral evidence → human Q2 view → approved → next task selection`.
- A test authored pure-logic PythonCode change goes through the same flow ending
  in a `pure-component-approval/1` record in `reborn_pure_component_approvals`
  with an associated `reborn_pure_evidence_submission_links` row.
- The approval record is immutable; a later body edit creates a new submission,
  not a mutation of the approved row.
- A fake human marker in the API body is rejected by the existing ingress.
- Model/component-management ports cannot write successful Q2 records.

### Step 10 — Production activation: internal validator routing and catalogue side-effects

**Owner:** `run_q1_validation_retained`, `RetainedValidatorCoverage`,
`authored_monty_catalogue.rs`, `pg_component_revision_store.rs`.

This step has two distinct sub-parts with different owners:

#### Step 10-A — Wire immutable-revision selection into the internal validator path

**Owner:** `run_q1_validation_retained` / `RetainedValidatorCoverage` /
`find_validator_recipe`.

Currently `find_validator_recipe` reads from the legacy mutable `reborn_recipes`
rows (the `validator-class-N` rows seeded by `seed_validator_recipes`). Step 10-A
switches it to select the immutable `ComponentRevisionDraft` envelopes from
`reborn_component_revisions` when they are present and have a valid
`pure-component-approval/1` record.

The validator Recipes are **internal routing entries** with `05:validator` consumer
tag. They are consumed exclusively by `find_validator_recipe` and
`run_q1_validation_retained` — **not** by the general user-matching catalogue
(`authored_monty_catalogue::prepare_with_policy`) used for Tier-0/1 routing.
The general catalogue remains unchanged by this sub-step.

Required work:
1. Extend `find_validator_recipe` to prefer the immutable revision path when
   `reborn_pure_component_approvals` has a valid record for the validator PC UUID,
   falling back to the legacy mutable row when none exists. **This fallback is a
   temporary compatibility measure only** — `validator_v3.md §Step 12` item 5
   requires retiring the legacy path after all tasks that selected it complete.
   Do not treat the fallback as a permanent design.
2. Verify that `RetainedValidatorCoverage::from_inputs()` and the downstream
   `compile_retained_recipe` / `prepare_retained_unbound_program` calls resolve
   the correct revision (the one with the class-specific PC body, not the legacy
   three-field structural body).
3. Keep the legacy mutable rows readable for any task that selected them; only
   newly admitted tasks use the new generation.

#### Step 10-B — Downstream reader carriage for validator approval pins

**Owner:** `authored_monty_catalogue.rs`, retained task selection, child/wait
and recovery readers (`pure-component-review.md` item 7, `simplified_v3.md §8.2`).

**The catalogue gate is already wired.** `authored_monty_catalogue::prepare_with_policy`
already calls `pg_pure_component_approval::load_independently_qualified` for
every non-binding step UUID (lines 463–486 of `authored_monty_catalogue.rs`),
querying `reborn_pure_component_approvals`. Once a validator PC has a
`pure-component-approval/1` record, it is automatically included in
`independently_qualified` — no new wiring is required for `prepare_with_policy`.

Required work:
1. Verify that `RetainedValidatorCoverage::validate_catalogue` (lines 603–606
   of `authored_monty_catalogue.rs`) correctly handles the approved validator
   PC state alongside the existing `independently_qualified` set.
2. Carry checksummed pure approval references through retained task selection,
   `child`/`wait` and recovery readers (`pure-component-review.md` item 7's
   second half): add checksummed pure references to catalogue
   serialization/restore/deployment, retained task selection, matching, private
   validator admission and recovery readers.
3. Follow `simplified_v3.md §8.2` for the publication cycle: publish the fully
   approved catalogue together with durable affected-prefix invalidation, then
   let the prefix owner build from that active snapshot.
4. Do not add validator Recipe revisions to the general user-matching catalogue.
   `05:validator`-tagged routes are excluded from ordinary matching in all
   generation states.

**Refer to `pure-component-review.md` items 6–7** (extend the independent
occurrence gate with real approvals; carry approval pins through every reader).

**Acceptance gate from `validator_v3.md §Step 10`:**
> Concurrent activation yields one complete old/new generation; an old waiting
> task continues its original code, while a live Tool block affects its next dispatch.

### Step 11 — Bootstrap, migration and upgrade

**Owner:** `component_boot.rs`, `builtin_bootstrap.rs`, `content_integrity.rs`,
`bootstrap_validator_approval.rs`.

1. Extend boot-time integrity to cover validator Recipe drafts in
   `reborn_component_revisions`. **Important:** `run_content_integrity_check`
   currently covers `reborn_skills`, `reborn_tool_skills` and `reborn_python_code`
   only (all with `source='system'` and `content_checksum` columns). A separate
   new query must verify the eight validator `ComponentRevisionDraft` rows in
   `reborn_component_revisions` by recomputing SHA-256 of the canonical JSON bytes
   and comparing against their stored revision checksums. A mismatch aborts boot,
   consistent with the existing pattern. This check must cover not just prose
   checksums but also the complete executable dependency/artifact chain per
   `validator_v3.md §Step 11` item 4: layout/bindings, the six class-specific PC
   body constants and actual Monty executable image identity.

2. Provide idempotent upgrade mapping: if a running instance has the legacy
   mutable `validator-class-N` rows (from `seed_validator_recipes`) and new
   immutable draft revisions are present (from `structural_validator_recipe_drafts`),
   the `bootstrap_validator_approval::qualify_all_validators` boot call must
   detect the existing legacy rows, retain the new immutable revisions idempotently
   and never overwrite an operator override. Also handle in-flight pending review
   submissions: if an operator started a review of a validator PC with the legacy
   body and the new immutable body is now seeded, the pending review must be
   flagged as superseded/incomplete — not silently adopted or failed. Per
   `validator_v3.md §Step 11` item 5: *"identify unsealed/incomplete reviews as
   needing review."* Preserve exact originals and their pending records.

3. Preserve old artifacts and evidence. Legacy `reborn_recipes` rows for the
   eight validators remain readable for any task that selected them; only
   newly admitted tasks select the new generation (via Step 10-A).

4. Ensure the `brassclaw repair` command re-seeds the validator revisions when
   their content checksums mismatch (per the existing `ON CONFLICT DO UPDATE`
   pattern in `repair.rs`).

**Acceptance gate from `validator_v3.md §Step 11`:**
> fresh/existing boot, repeated boot, upgrade with overrides, interrupted
> review/commit and restore preserve trust and task retention without invented passes.

### Step 12 — WebUI/API and production cutover

**Owner:** WebUI `settings-tabs.js`, `pg_settings_listing.rs`,
`crates/brassclaw_product_workflow/src/settings.rs`,
`crates/brassclaw_reborn_webui_ingress/…`.

1. **Show class-route detail in the WebUI component catalog:**
   - For each `validator-class-N` Recipe in the Settings → Component Catalog tab,
     display: draft revision, active revision (if any), exact validator selection,
     check failures, missing evidence, behavioral observations and human Q2 status.
   - Show the *reviewed combination*, not a display recomputed from latest mutable rows.

2. **Preserve pending/failed/incomplete/rejected states** and resubmission:
   disabling approval when backend gates are incomplete; the UI is not the gate.

3. **Support operator editing** of validator Recipes and associated PythonCode
   through immutable versions and the same Q1/behavior/Q2 contract. Do not expose
   success-evidence writes or mutable approved-body editing.

4. **Production acceptance matrix** (from `validator_v3.md §5`):
   - All eight class routes: valid candidate reaches required gates; distinct
     invalid candidate is rejected for its class defect.
   - Metadata/source separation: hostile strings remain data; checksum unchanged.
   - Full Recipe inspection: empty steps, bad links, multiple UUIDs, unpaired
     bindings and invalid result edges fail.
   - **Complete Skill:** Missing association, multi-Tool purpose and prose/code
     disagreement do not pass final approval (class-1/2/3 routes).
   - **Interface integrity/selection:** Changing only an export/signature/fixed
     argument changes the reviewed Skill content/combination; undeclared symbols,
     incompatible aliases and ambiguous multiple exports fail before effects.
     Association formats remain unchanged.
   - **Mutable invocation isolation:** Repeated/concurrent invocations get fresh
     mutable defaults/arguments/arrays/results. Shared mutable globals/caches and
     closures over foreign inputs/host context fail.
   - **Export/host generation coexistence:** Activate a successor during an old
     task's wait — both use their own interface/code/host implementation.
   - **Deterministic export loading:** Dependency-first order with stable-UUID
     ties is repeatable; missing helpers, cycles, conflicting names and undeclared
     imports fail.
   - Human/provenance: fake human flags, old receipts and self-issued evidence fail.
   - Authored production end-to-end: actual installed submission → pinned validator
     exports → evidence → human Q2 → publication → next matched task works.
   - Bundled production end-to-end: reviewed installation package → noncircular
     integrity/Q1/behavior → system_seed records with null Q2 → coherent publication.

5. **Replace the legacy Q1 entry path** only after the above acceptance matrix
   is complete. The legacy `seed_validator_recipes` `validation_status='validated'`
   path is already bypassed by `run_q1_validation_retained`; no second removal
   is required, but the legacy mutable rows must remain readable until all
   running tasks that may have selected them have completed. Also remove
   `executor/code_audit.rs` (the orphaned Rust audit workflow) after verifying
   no active caller uses it, per `validator_v3.md §Step 12` item 5.

6. Update `docs/implementation-status.md` with a dated entry recording:
   - Commits for each step (9 through 12).
   - Confirmation that the human Q2 path for authored changes covers classes 21 and 22.
   - Confirmation that `find_validator_recipe` selects the immutable revision path.
   - Confirmation that the production acceptance matrix cases passed.

  TASK-022 only.

- **L013–L101 component qualification** — covered by `missing2_v3_at_k3.md`
  and `bootstrap_l013_approval.rs`. Not touched here.

- **TASK-022 T2–T5 retest** — tracked separately. A prerequisite, not a
  deliverable of this plan.

- **General standalone pure approval** — `pure-component-review.md` items 1–8
  belong specifically to **validator Steps 3/8–10** and are this plan's
  deliverables. V35-03/04 and composition R10 *consume* that implementation;
  they do not own it. Implement all eight cutover-contract items here. The
  general standalone pure approval for arbitrary operator-authored
  *non-validator* pure components remains separate open work, but the eight
  contract items themselves must be closed by this plan.

- **MCP publication** — having behavioral evidence and approval records for
  validator Recipes does not publish them as MCP commands. They are internal
  private routes (`05:validator` tag) and must remain excluded from ordinary
  user matching.

- **prefix Phase C2/C3/D** — Step 10-B's catalogue publication triggers prefix
  invalidation; the prefix *owner* builds from the active snapshot. This plan
  does not implement prefix generation or serving.

- **Dynamic occurrences (V35-13/14)** — conditional/repeated check coverage in
  Steps 7–8 requires the occurrence/control owner to supply qualified control
  primitives. Until those are available, validator workflows that require
  conditional branching over class-specific check sub-sets remain as drafts.

- **Classes 10/50 (Orchestrator/Scaffold) roots** — Step 7's requirement note
  states these must not be accidentally certified by a generic class-1/2/3
  route. Their coordinated review is an explicit dependency; no generic validator
  route may certify them.

  controlled seed path with `q2_ref = null`. `bootstrap_validator_approval.rs`
  already implements this correctly. An installed operator edit requires
  the authored Q1/behavior/human-Q2 path (Steps 9/12).

- **Association is embedded in the revision, not a standalone row.** The
  `"association"` field of the `"component-revision/1"` envelope must be embedded
  in `reborn_component_revisions` (same pattern as `missing2_v3_at_k3.md` §6).

- **One UUID per component step.** `validator-class-N` Recipes follow the
  one-UUID-per-`include` rule; the current structural scaffold already enforces this.

- **Candidate JSON is string data decoded by `json.loads(inputs["content"])`.** The
  validator PC bodies decode the component's `content` field (a JSON string)
  using `import json`. The validator body must never `eval()` or `exec()` candidate
  source. The input key is `inputs["content"]`, not `inputs["candidate_json"]`.

- **`retain_completed` is the correct writer for Tool-calling pairs only.**
  `bootstrap_evidence::retain_completed` writes atomically to both
  `reborn_component_review_evidence` AND `reborn_skill_association_approvals`.
  It is the correct path for class-1 Skill/PythonCode pairs. For pure-logic
  components (validator PCs), the correct path is: write behavioral evidence
  directly to `reborn_component_review_evidence`, then call
  `record_pure_component_approval` which writes to `reborn_pure_component_approvals`.
  Do not use `retain_completed` for pure-logic components.

- **`record_pure_component_approval` verifies evidence existence and `succeeded=true`**
  before inserting. It checks all evidence UUIDs in `reborn_component_review_evidence`
  and all component revisions in `reborn_component_revisions`; an approval
  declaration referencing a missing or failed evidence row is rejected.

- **All approval UUIDs are deterministic (UUID v5)** derived from component bytes
  + a fixed namespace constant. Re-runs produce no duplicate inserts.

- **`run_q1_validation_retained` is the sole production Q1 entry point.**
  No second Q1 path, validator-specific scheduler or Rust sweep loop is introduced.

- **Validator Routes are internal only.** `05:validator`-tagged Recipes are
  excluded from ordinary user matching and must not appear in the general
  user-visible catalogue generation. Step 10-A wires them through the internal
  `find_validator_recipe` / `RetainedValidatorCoverage` path; Step 10-B handles
  only the approval-pin carriage in downstream readers — the catalogue gate in
  `prepare_with_policy` is already implemented.

- **Draft containment.** Draft validator Recipe revisions are assembled and
  tested only in the constrained review environment. Ordinary matching sees only
  the coherent active approved catalogue.

- **`reborn_pure_evidence_submission_links` (V201) must be used for authored Q2.**
  `pg_pure_component_approval.rs` lines 298–310 document the link-writing API.
  All new pure-evidence writes for authored Q2 (Step 9) must go through this path
  to bind each `submission_id` to its `approval_id`, tying the pure approval to
  the exact review subject (`pure-component-review.md` item 1).

- **No new outbox, queue framework or polling loop for Step 9.** Step 9 binds
  immutable submissions into the **existing shared review-runtime contract**
  (`simplified_v3.md`). Simplified implements request/run idempotency,
  wake/reconciliation and execution ownership; this plan supplies exact
  submission/subject/validator/check-set references only. Per
  `validator_v3.md §Step 9` item 1.
